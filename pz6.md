# **Практическое задание № 6. Интеграция Bash и Python: разработка системы автоматизированного администрирования Linux**

**Модуль 6. Интеграция и практические кейсы**

## **Цель**

Научиться объединять Bash и Python в единую систему автоматизации системного администрирования, распределять задачи между инструментами, обеспечивать корректный обмен данными и разрабатывать решения для типовых ситуаций, возникающих при эксплуатации Linux-серверов.

В ходе практической работы необходимо:

- Освоить совместное использование Bash и Python в одном проекте автоматизации.
- Научиться передавать параметры, результаты выполнения и коды завершения между Bash-скриптами и Python-программами.
- Реализовать автоматизированную диагностику состояния Linux-системы.
- Разработать механизм анализа системных журналов и выявления потенциальных неисправностей.
- Реализовать резервное копирование важных файлов с контролем результатов.
- Научиться обрабатывать частичные отказы и продолжать выполнение независимых операций.
- Разработать единую CLI-утилиту для управления административными процедурами.
- Проверить работоспособность системы на практических сценариях, имитирующих реальные проблемы эксплуатации серверов.

## **Задание (шаги)**

### **Шаг 1. Подготовка проекта и организация взаимодействия Bash и Python**

Необходимо создать проект автоматизации системного администрирования, состоящий из Bash-скрипта и Python-программы.

1. Создать рабочий каталог `integrated_admin`.
2. Внутри него создать следующие подкаталоги:
   - `scripts` — Bash-скрипты;
   - `src` — Python-программы;
   - `data` — тестовые журналы и конфигурационные файлы;
   - `backups` — резервные копии;
   - `reports` — отчёты о состоянии системы;
   - `logs` — журналы выполнения автоматизации;
   - `config` — конфигурационные файлы.
3. Создать Bash-скрипт `scripts/run_admin.sh`.
4. Создать Python-программу `src/admin_tool.py`.
5. Создать конфигурационный файл `config/settings.json`.
6. Проверить доступность Python из командной строки Linux.
7. Настроить Bash-скрипт для запуска Python-программы.
8. Реализовать передачу аргументов из Bash в Python.
9. Обеспечить получение Bash-скриптом кода завершения Python-программы.
10. Проверить, что запуск проекта выполняется из корневого каталога командой:

```
bash scripts/run_admin.sh --mode check
```

**Распределение ответственности между компонентами:**

| Компонент       | Назначение                                                                             |
| --------------- | -------------------------------------------------------------------------------------- |
| `run_admin.sh`  | Подготовка окружения, запуск системных команд, управление последовательностью операций |
| `admin_tool.py` | Анализ данных, вычисление статистики, резервное копирование и формирование отчётов     |
| `settings.json` | Хранение настроек автоматизации                                                        |
| `logs/`         | Регистрация событий и ошибок                                                           |
| `reports/`      | Хранение результатов диагностики                                                       |
| `backups/`      | Хранение резервных копий                                                               |

**Ожидаемый результат:** Создан проект, в котором Bash отвечает за организацию выполнения системных операций, а Python — за обработку данных и реализацию основной логики.

### **Шаг 2. Реализация конфигурации системы**

Необходимо создать единый конфигурационный файл для настройки автоматизации без изменения исходного кода.

В `config/settings.json` сохранить следующую структуру:

```
{
  "source_dir": "data",
  "backup_dir": "backups",
  "report_dir": "reports",
  "log_dir": "logs",
  "disk_warning_percent": 80,
  "error_critical_count": 3,
  "max_backup_count": 3
}
```

Реализовать следующую логику:

1. При запуске Python-программы загружать конфигурацию из файла.
2. Проверять существование файла конфигурации.
3. Проверять корректность JSON.
4. Проверять наличие всех обязательных параметров.
5. Проверять типы и допустимые значения настроек.
6. Преобразовывать относительные пути в абсолютные относительно корневого каталога проекта.
7. Запрещать использование каталога резервных копий, совпадающего с исходным каталогом или расположенного внутри него.
8. При обнаружении некорректной конфигурации выводить сообщение об ошибке.
9. Сохранять информацию о проблеме в журнале.
10. Не запускать операции резервного копирования при критических ошибках конфигурации.

Предусмотреть возможность изменения порогового значения заполнения диска и максимально допустимого количества резервных копий через файл настроек.

**Ожидаемый результат:** Программа использует внешнюю конфигурацию, проверяет её корректность и позволяет изменять параметры работы без редактирования Bash- и Python-кода.

### **Шаг 3. Автоматизированная диагностика Linux-системы**

Необходимо реализовать механизм проверки состояния сервера с использованием Bash и Python.

**Часть А. Сбор системной информации через Bash**

В `run_admin.sh` реализовать выполнение диагностических команд:

| Команда    | Получаемая информация                        |
| ---------- | -------------------------------------------- |
| `hostname` | Имя сервера                                  |
| `uptime`   | Время непрерывной работы системы             |
| `df -P`    | Информация об использовании файловой системы |
| `free -m`  | Использование оперативной памяти             |
| `whoami`   | Имя пользователя                             |

Для каждой команды необходимо:

1. Выполнить команду из Bash-скрипта.
2. Проверить код завершения.
3. Получить стандартный вывод.
4. Сохранить результаты в отдельные временные файлы.
5. При возникновении ошибки записать диагностическое сообщение.
6. Передать путь к каталогу с результатами Python-программе.

Временные файлы рекомендуется создавать с помощью `mktemp -d`, а после завершения обработки удалять средствами Bash.

**Часть Б. Анализ данных в Python**

Реализовать функцию `analyze_system()`.

Она должна:

1. Прочитать результаты системных команд.
2. Определить имя сервера.
3. Получить сведения о времени работы.
4. Определить процент использования файловой системы, содержащей рабочий каталог проекта.
5. Получить информацию об оперативной памяти.
6. Сравнить использование диска с параметром `disk_warning_percent`.
7. Сформировать словарь с результатами диагностики.
8. Передать результаты в модуль формирования отчётов.

Для дискового пространства использовать следующие состояния:

| Условие                                      | Состояние |
| -------------------------------------------- | --------- |
| Заполненность ниже установленного порога     | `OK`      |
| Заполненность равна порогу или превышает его | `WARNING` |
| Не удалось получить показатели               | `UNKNOWN` |

Пример результата:

```
========== SYSTEM DIAGNOSTICS ==========

Hostname: linux-server
User: student
Uptime: 3 days

Disk usage: 65%
Disk threshold: 80%
Disk status: OK

Memory total: 4096 MB
Memory used: 2048 MB

Diagnostics completed.
```

**Ожидаемый результат:** Bash собирает системные показатели, а Python анализирует их и определяет состояние сервера.

### **Шаг 4. Автоматизированный анализ системных журналов**

Необходимо разработать механизм обнаружения ошибок в журналах приложений.

В каталоге `data` создать два файла: `application.log` и `system.log`.

**Содержимое&#x20;**`application.log`**:**

```
2026-11-20 09:00:00 INFO api started
2026-11-20 09:01:00 WARN api slow_response
2026-11-20 09:02:00 ERROR db connection_failed
2026-11-20 09:03:00 INFO api request_ok
2026-11-20 09:04:00 ERROR api timeout
2026-11-20 09:05:00 WARN auth suspicious_login
2026-11-20 09:06:00 INFO auth login_ok
```

**Содержимое&#x20;**`system.log`**:**

```
2026-11-20 10:00:00 INFO system started
2026-11-20 10:01:00 ERROR storage write_failed
2026-11-20 10:02:00 INFO backup started
2026-11-20 10:03:00 WARN backup slow_operation
2026-11-20 10:04:00 ERROR backup archive_failed
```

Создать функцию `analyze_logs()`, которая:

1. Находит все файлы с расширением `.log` непосредственно в каталоге `data`.
2. Последовательно открывает найденные файлы.
3. Проверяет формат каждой записи.
4. Выделяет дату, время, уровень, компонент и описание события.
5. Подсчитывает количество событий `INFO`, `WARN` и `ERROR`.
6. Группирует ошибки по компонентам.
7. Определяет количество ошибок в каждом файле.
8. Выявляет компонент с наибольшим количеством ошибок.
9. Сохраняет найденные ошибки в `reports/critical_events.txt`.
10. Формирует общую статистику.

Для анализа использовать строковые методы, словари, циклы и регулярные выражения.

**Правила классификации результатов:**

| Условие                                                       | Уровень    |
| ------------------------------------------------------------- | ---------- |
| Нет ошибок и предупреждений                                   | `OK`       |
| Есть предупреждения, но ошибок меньше критического порога     | `WARNING`  |
| Количество ошибок равно критическому порогу или превышает его | `CRITICAL` |

Критический порог определяется параметром `error_critical_count`.

**Контрольные результаты:**

| Показатель                  | Значение |
| --------------------------- | -------- |
| Всего событий               | 12       |
| INFO                        | 5        |
| WARN                        | 3        |
| ERROR                       | 4        |
| Ошибки компонента db        | 1        |
| Ошибки компонента api       | 1        |
| Ошибки компонента storage   | 1        |
| Ошибки компонента backup    | 1        |
| Итоговое состояние журналов | CRITICAL |

Если несколько компонентов имеют одинаковое максимальное количество ошибок, программа должна корректно учитывать все такие компоненты.

**Ожидаемый результат:** Реализован механизм анализа журналов, позволяющий автоматически обнаруживать ошибки и определять уровень критичности событий.

### **Шаг 5. Создание системы резервного копирования**

Необходимо реализовать автоматизированное создание резервных копий важных файлов.

Создать функцию `create_backup()`.

Она должна выполнять следующие действия:

1. Определить исходный каталог на основании конфигурации.
2. Найти файлы с расширениями `.log` и `.conf`.
3. Исключить остальные типы файлов.
4. Проверить существование каталога `backups`.
5. При необходимости создать каталог резервных копий.
6. Создать архив формата `.tar.gz`.
7. Добавить дату и время создания в название архива.
8. Сохранить структуру относительных путей файлов.
9. Проверить целостность структуры созданного архива и возможность его чтения.
10. Сохранить информацию о резервной копии в журнале.

Пример названия:

```
backup_2026-11-20_143000.tar.gz
```

**Дополнительное требование — ограничение количества резервных копий.**

Необходимо реализовать автоматическую ротацию архивов.

1. Получить список архивов, созданных программой.
2. Отсортировать архивы по времени создания.
3. Получить допустимое количество резервных копий из `max_backup_count`.
4. Если количество архивов превышает ограничение, определить самые старые архивы.
5. Удалить только избыточные архивы, принадлежащие проекту.
6. Записать информацию об удалении в журнал.

Например, при `max_backup_count = 3` после создания четвёртой копии должна остаться тройка наиболее новых архивов.

**Ограничение:** Удаление разрешено только в специально выделенном каталоге `backups` и только для архивов, созданных программой. Нельзя удалять исходные файлы, произвольные архивы пользователя или содержимое системных каталогов.

Также необходимо реализовать режим `--dry-run`, при котором программа показывает планируемые действия, но не создаёт и не удаляет архивы.

**Ожидаемый результат:** Программа автоматически создаёт резервные копии, проверяет их доступность и контролирует количество хранящихся архивов.

### **Шаг 6. Разработка единого CLI-интерфейса**

Необходимо объединить все операции в единый интерфейс командной строки.

Основной точкой входа должен быть Bash-скрипт `run_admin.sh`.

Он должен поддерживать следующие режимы:

| Режим    | Назначение                    |
| -------- | ----------------------------- |
| `check`  | Диагностика состояния сервера |
| `logs`   | Анализ журналов               |
| `backup` | Создание резервной копии      |
| `full`   | Выполнение всех операций      |

Реализовать следующие параметры:

| Параметр    | Назначение                             |
| ----------- | -------------------------------------- |
| `--mode`    | Выбор режима выполнения                |
| `--config`  | Путь к конфигурационному файлу         |
| `--dry-run` | Проверка без изменения резервных копий |
| `--help`    | Вывод справки                          |

Примеры запуска:

**Диагностика системы:**

```
bash scripts/run_admin.sh --mode check
```

**Анализ журналов:**

```
bash scripts/run_admin.sh --mode logs
```

**Резервное копирование:**

```
bash scripts/run_admin.sh --mode backup
```

**Комплексное выполнение:**

```
bash scripts/run_admin.sh --mode full
```

**Проверка без изменения резервных копий:**

```
bash scripts/run_admin.sh --mode full --dry-run
```

Необходимо реализовать следующий механизм взаимодействия:

1. Bash получает аргументы командной строки.
2. Bash проверяет корректность выбранного режима.
3. Bash определяет расположение Python-программы.
4. Bash выполняет необходимые системные команды.
5. Bash передаёт Python результаты диагностики через временные файлы.
6. Python выполняет анализ данных и необходимые операции.
7. Python сохраняет результаты и возвращает код завершения.
8. Bash проверяет код завершения Python-программы.
9. Bash выводит пользователю итоговый статус.

**Ожидаемый результат:** Все административные операции выполняются через единую CLI-утилиту с понятными параметрами.

### **Шаг 7. Обработка ошибок и частичных отказов**

Необходимо обеспечить устойчивую работу всей системы при возникновении проблем.

**Часть А. Обработка ошибок Bash**

Предусмотреть:

1. Отсутствие установленного Python.
2. Отсутствие Python-файла.
3. Некорректные аргументы командной строки.
4. Ошибки выполнения системных команд.
5. Ошибки создания временных файлов.
6. Ненулевой код завершения Python-программы.

Для повышения надёжности использовать `set -euo pipefail`, проверки кодов завершения и `trap`.

**Часть Б. Обработка ошибок Python**

Предусмотреть:

1. Отсутствие конфигурационного файла.
2. Некорректный JSON.
3. Отсутствие исходного каталога.
4. Ошибки чтения системных журналов.
5. Недостаточные права доступа.
6. Ошибки создания архива.
7. Ошибки записи отчётов.
8. Ошибки удаления старых резервных копий.

Для обработки исключений использовать `try-except` и журналирование.

**Часть В. Независимость операций**

В режиме `full` необходимо обеспечить продолжение остальных независимых проверок при ошибке одного из этапов.

Например, если анализ журналов завершился ошибкой, но система доступна для диагностики и резервного копирования, соответствующие операции должны быть выполнены.

Для оценки успешности автоматизации использовать следующие статусы:

| Статус    | Значение                                               |
| --------- | ------------------------------------------------------ |
| `SUCCESS` | Все запрошенные операции выполнены успешно             |
| `PARTIAL` | Часть операций выполнена, часть завершилась с ошибками |
| `FAILED`  | Ни одна из запрошенных операций не выполнена успешно   |

Статус выполнения не должен смешиваться с уровнем обнаруженных проблем. Например, диагностика может завершиться успешно (`SUCCESS`), но выявить критическое состояние журналов (`CRITICAL`).

**Ожидаемый результат:** Программа обрабатывает возникающие ошибки, сохраняет результаты успешных операций и корректно сообщает об итоговом состоянии.

### **Шаг 8. Формирование комплексного отчёта**

Необходимо реализовать автоматическое формирование отчётов о результатах выполнения административных операций.

Создать функцию `generate_report()`, которая сохраняет результаты в `reports/admin_report.json`.

Отчёт должен содержать:

1. Дату и время выполнения.
2. Режим запуска программы.
3. Информацию о сервере.
4. Результаты проверки дискового пространства.
5. Сведения об оперативной памяти.
6. Статистику системных журналов.
7. Результаты резервного копирования.
8. Список ошибок выполнения.
9. Итоговый статус автоматизации.

Пример структуры отчёта:

```
{
  "timestamp": "2026-11-20T14:30:00",
  "mode": "full",
  "system": {
    "hostname": "linux-server",
    "disk_usage": 65,
    "disk_status": "OK"

Также необходимо создать текстовый отчёт `reports/admin_report.txt`, содержащий основные результаты диагностики в удобном для чтения формате.

Все тестовые изменения должны выполняться только внутри рабочего проекта.

### **1. Вызов Python из Bash**

Для выполнения Python-программы можно использовать:

```

Результат выполнения Python-программы можно проверить непосредственно в условии:

if python3 src/admin_tool.py --mode check; then

else

    echo "Ошибка диагностики. Код: $status" >&2

```

Такой способ позволяет корректно обработать ненулевой код завершения при использовании `set -e`.

Перед удалением необходимо гарантировать, что переменная содержит путь к созданному временному каталогу. В промышленной реализации дополнительно рекомендуется проверять путь и ограничивать область возможного удаления.

### **7. Обработка ошибок**

В Python рекомендуется использовать обработку конкретных исключений.

```
try:    result = perform_operation()except FileNotFoundError as error:    print(f"Файл не найден: {error}")except PermissionError as error:    print(f"Нет доступа: {error}")except OSError as error:    print(f"Ошибка файловой системы: {error}")else:    print("Операция завершена успешно")

Необходимо различать ожидаемые ошибки выполнения отдельных операций и ошибки, после которых дальнейшая работа программы невозможна.

## **Советы по улучшению работы**

1\. **Разделение ответственности между Bash и Python.** Bash целесообразно использовать для запуска системных команд, подготовки окружения и координации процессов, а Python — для сложной обработки данных, анализа журналов и формирования структурированных отчётов.

2\. **Модульная организация Python-кода.** По возможности разделить программу на модули `system_check.py`, `log_analyzer.py`, `backup.py` и `reporting.py`. Это упростит дальнейшее развитие проекта.

3\. **Использование единой конфигурации.** Не рекомендуется дублировать пути и пороговые значения в нескольких файлах. Все настройки, которые могут изменяться, желательно хранить в конфигурационном файле.

4\. **Безопасная работа с файловой системой.** Перед удалением архивов проверять расположение файлов, корректность путей и принадлежность архивов проекту. Не использовать рекурсивное удаление без предварительных ограничений.

5\. **Повышение надёжности резервного копирования.** После создания архива проверять не только его наличие, но и возможность чтения содержимого. При необходимости можно дополнительно сравнивать хеш-суммы файлов.

6\. **Предотвращение параллельных запусков.** Для автоматизации по расписанию рекомендуется использовать блокировку, например через `flock`, чтобы несколько экземпляров программы одновременно не изменяли один и тот же набор архивов и отчётов.

7\. **Повышение качества журналирования.** Использовать модуль `logging` в Python и единый формат сообщений, содержащий временную метку, уровень, название компонента и описание события.

8\. **Разделение статусов выполнения и состояния сервера.** Успешное выполнение диагностики не означает отсутствие проблем на сервере. В отчёте желательно отдельно хранить статус операции и обнаруженный уровень критичности.

9\. **Автоматизированное тестирование.** Для проверки функций анализа логов, конфигурации и резервного копирования можно использовать `unittest` или `pytest`, а системные показатели подменять тестовыми данными.

10\. **Расширение системы до нескольких серверов.** В качестве дополнительного развития можно использовать SSH для удалённого выполнения диагностических команд, централизованного сбора результатов и формирования общего отчёта по инфраструктуре.
